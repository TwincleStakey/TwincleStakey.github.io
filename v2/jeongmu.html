CASE 01 · NETCODE

게스트 화면에서는 안 맞는 공격

맞는 쪽 판정 + 공격자가 보던 시각으로 되감기 · 개발 빌드 두 개로 실측

문제

게스트로 들어가면 당문 비도가 화면에서는 분명히 맞았는데 피해가 안 들어갔다. 사자후는 기절 별만 뜨고 피해는 0이었다. 일치율을 재 보니 비도는 15%였다.

제약

판정은 맞는 쪽 PC가 한다는 구조는 바꾸고 싶지 않았다. 막기·튕겨내기가 맞는 쪽 입력이라서다. 전용 서버도 없다. 방장이 곧 플레이어다. 에디터 두 개로 재면 포커스 없는 쪽이 1초마다 0.5초씩 멈춰 핑이 600~900ms로 튀었다.

선택지
  • 공격자 화면 기준으로 판정을 옮긴다 → 막는 사람의 반응이 무시된다
  • NGO 보간 버퍼만 줄인다 → 핑이 튀면 끊긴다
  • 맞는 쪽 판정은 두고, 공격자가 보던 시각으로 내 위치를 되감아 잰다
결정

소유자가 12ms 간격으로 자기 위치를 남겨 두고, 다른 PC의 공격은 "그 PC가 나를 그리던 지연"만큼 되감은 자리로 잰다. 막기·무적 같은 막는 쪽 상태는 지금 기준 그대로다.

되감기 시간은 방장·게스트 조합마다 다르다는 걸 실측으로 알았다. 처음엔 한 공식으로 쓰다가 게스트끼리 비도가 59%였다. 방장 몸은 게스트 PC의 보간 버퍼만큼 더 늦게 그려지고, 게스트 몸은 이미 늦은 시각이 찍혀 와 도착하는 대로 그려진다. 게스트 PC의 보간은 NGO 기본 Lerp 대신 고정 3틱으로 바꿨다. 기본 Lerp는 버퍼를 왕복 지연만큼 키우고 핑 스파이크를 몇 초씩 끌고 갔다.

근거

개발 빌드 두 개를 -host / -join / -autoplay / -lag 60 -jitter 10으로 띄워 AI끼리 싸우게 하고, 5초마다 "내 화면에서 닿음 → 실제로 맞음" 비율을 기록했다. 오른쪽 수치와 코드.

한계

되감기 상한이 0.25초라 그보다 느린 회선에서는 다시 어긋난다. 측정은 같은 PC의 빌드 두 개 + 시뮬 지연이라 실제 공유기 환경의 수치는 다를 수 있다. 사람 둘이 실제로 한 판의 일치율은 따로 재지 못했다.

Duelist.cs · ViewDelayOf / HitPosition// 이 공격자의 PC가 내 몸을 얼마나 늦게 그리는지 (초). 같은 PC(방장의 AI 포함)면 0
float ViewDelayOf(Duelist attacker)
{
    if (attacker == null || attacker.IsOwner || nm == null || !nm.IsListening) return 0f;
    bool attackerIsHost = attacker.OwnerClientId == NetworkManager.ServerClientId;
    float attackerOneWay = attackerIsHost ? 0f
        : nm.IsServer ? transport.GetCurrentRtt(attacker.OwnerClientId) / 2000f : OneWay;
    // 빌드 실측(편도 60±10ms): 방장 몸 → 게스트 화면 170ms, 게스트 몸 → 방장 화면 90ms
    // 방장 몸은 게스트 PC의 보간 버퍼(서버 버퍼 50ms + 3틱)만큼 더 늦게 그려지고,
    // 게스트 몸은 '이미 늦은' 시각이 찍혀 와서 버퍼 없이 도착하는 대로 그려진다
    float delay = IsServer ? attackerOneWay + 0.05f + 3f / 60f
                           : OneWay + attackerOneWay + (attackerIsHost ? 0.02f : 0.01f);
    return Mathf.Min(MaxRewind, delay);   // 상한 0.25초
}

// 다른 PC의 공격을 잴 때 쓰는 내 위치 — 12ms 간격으로 남긴 위치 기록(약 0.75초치)을 되감는다
public Vector3 HitPosition(Duelist attacker) => PositionAgo(ViewDelayOf(attacker));

CASE 02 · MEASUREMENT

측정 환경을 바꾸고 나서야 보인 원인

에디터 측정을 버리고 개발 빌드 두 개로 · 비도 출발점 통일

문제

되감기를 넣은 뒤에도 에디터에서 비도 일치율이 38~60% 사이를 오갔다. 처음엔 에디터 멈춤 탓이라고 봤다.

제약

포커스 없는 에디터는 플레이 중 게임 루프가 거의 안 돈다. 49초에 3프레임이었다. 플레이어 루프를 강제로 돌려도 1초마다 0.5초씩 화면 출력 대기에 걸렸다. 이 멈춤이 섞인 숫자는 믿을 수 없었다.

선택지
  • 멈춘 구간만 빼고 분석한다 → 매번 손으로 골라야 한다
  • 에디터에 루프 펌프를 건다 → 멈춤은 줄지만 0은 아니다
  • 측정 환경 자체를 개발 빌드 두 개로 바꾼다
결정

정식 빌드와 따로 개발 빌드를 만들고 실행 인자로 방장·손님·자동 대전·지연 시뮬·일치율 기록을 켤 수 있게 했다. 같은 PC에서 창 두 개면 충분했다.

그러자 원인이 보였다. 던지는 사람 화면만 지금 자리에서 비도를 날리고 있었다. 걸으며 던지면 움직인 만큼, 최대 0.8m까지 궤적이 갈라졌다. 모든 화면이 시전 시점의 출발점에서 날리게 통일했다.

근거

비도 91%(93/102), 전체 95%, 근접 97%. 이걸 원칙으로 적어 두었다. 시간이 지나 나가는 암기는 쏘는 사람이 출발점·방향을 정해 RPC로 보낸다. 뒤에 새 초식(폭우연사)이 이 원칙을 깨 91%가 76%로 떨어진 것도 같은 측정으로 잡아 89%로 되돌렸다.

한계

일치율 도구는 "내 화면에서 닿음 → 실제 맞음"만 센다. 반대 경우, 화면에선 빗나갔는데 맞은 것은 세지 않는다. 자동 대전은 AI 움직임이라 사람의 경공·페인트는 담기지 않는다.

CASE 03 · WINDOWS · UNITY 내부

다른 PC에서 커서가 너무 작다

오진 한 번 → 유니티가 커서를 32px로 줄인다는 확인 → Win32로 직접 만들어 창에 걸기

문제

다른 PC에서 커서가 작았다. 설정에서 키워도 그대로였다. 내 PC에서는 괜찮아 보여서 더 늦게 알았다.

제약

윈도우 빌드다. 되도록 유니티 API 안에서 풀고 싶었다. 녹화에 커서가 찍히면 안 돼서 소프트웨어 커서는 피하고 싶었다.

선택지
  • "하드웨어 커서는 64px 고정"이라 보고 크기별 이미지 11벌 → 오진. 바뀌지 않았다
  • ForceSoftware 커서 → 녹화에 찍히고 한 프레임 늦다
  • Win32로 커서를 직접 만들어 게임 창에 건다
결정

원인을 다시 봤다. 윈도우에서 유니티 Cursor.SetCursor는 그림 크기와 상관없이 윈도우 기본 커서 칸(100% 배율에서 32px)으로 줄인다. UnityPlayer.dll이 LoadImage/CopyImage만 쓴다.

CreateIconIndirect로 커서를 원본 크기로 만들고, 게임 창 WndProc를 가로채 WM_SETCURSOR에서 우리 커서를 건다. 그래도 유니티가 매 프레임 자기 화살표를 다시 걸어 깜빡였다. 그래서 UnityPlayer.dll 가져오기 표(IAT)의 SetCursor 칸을 우리 함수로 바꿔 끼웠다. 창을 가두는 것도 ClipCursor로 직접 한다. 종료 때 전부 되돌린다.

근거

빌드 실측 — 설정 50/100/200% = 32/64/128px, 원 그리기·오른쪽 누름 중 화살표 깜빡임 0번, 정상 종료. 크기 공식은 64 × max(1, 모니터 높이/1080) × 설정값으로, 어느 PC에서나 같은 크기다.

한계

윈도우 x64 전용이다. 에디터와 다른 OS는 유니티 커서 그대로다. UnityPlayer.dll 내부 가져오기 표 구조에 기대고 있어 엔진 버전이 바뀌면 다시 확인해야 한다. 오진으로 만든 11벌의 이미지는 결국 크기 단계용으로 남겼다.

DuelCursor.cs · Win.PatchUnitySetCursor// UnityPlayer.dll 가져오기 표(IAT)에서 USER32.dll SetCursor 칸을 찾아 바꿔 끼운다 (64비트 PE)
static void PatchUnitySetCursor()
{
    var module = GetModuleHandle("UnityPlayer.dll");
    int pe = Marshal.ReadInt32(module, 0x3C);
    int imports = Marshal.ReadInt32(module, pe + 24 + 120); // 데이터 디렉터리 1번 = 가져오기
    for (int d = imports; ; d += 20)
    {
        int names = ReadInt32(module, d), dll = ReadInt32(module, d + 12), slots = ReadInt32(module, d + 16);
        if (dll == 0) return;
        if (PtrToStringAnsi(module + dll) != "USER32.dll") continue;
        for (int i = 0; ; i++)
        {
            long thunk = Marshal.ReadInt64(module, names + i * 8);
            if (thunk == 0) return;
            if (thunk < 0 || PtrToStringAnsi(module + (int)thunk + 2) != "SetCursor") continue;
            iatSlot = module + slots + i * 8;
            realSetCursor = Marshal.ReadIntPtr(iatSlot);
            WriteSlot(Marshal.GetFunctionPointerForDelegate(unitySetCursor));
            return;
        }
    }
}

  • 자동 대전 밸런스 — 마교 86% → 76%, 당문 17% → 32% (50~150판, 미러 제외).

다시 하면 다르게

  • 측정 환경부터 의심한다. 에디터 숫자로 이틀을 썼다. 빌드 두 개는 반나절이었다.
  • 오진을 기록한다. 커서 11벌은 틀린 가설의 흔적이고, 그래서 다음엔 GetCursor부터 봤다.
  • 원칙은 문서로 남긴다. 투사체 RPC 원칙을 적어 두어서 새 초식의 회귀를 숫자로 잡았다.
아직 확인 전 싱글(스토리) 모드, 관전·재접속, 서로 다른 PC 간 랭크 실전은 코드는 있으나 플레이 기록이 없어 여기 넣지 않았다.
